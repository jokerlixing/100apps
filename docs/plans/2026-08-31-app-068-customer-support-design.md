# App 068 智能客服机器人设计

## 产品边界与用户路径

68 号应用命名为 **RELAY/68**，服务于需要快速、稳定回答售前与售后问题的小型网店客服。页面只承担一条主路径：客户提出问题，系统识别意图，从当前启用的 FAQ 知识库中找到依据，先给出一条可审计的本地回复，再在服务器已配置时尝试 AI 增强。每条回答都显示意图、置信度和引用知识卡；找不到可靠依据时明确进入人工接管，不编造订单、退款或物流状态。

默认知识库覆盖订单、物流、退换货、退款、支付、发票、账户、商品与优惠九类常见问题。客服可以搜索、启停、添加、修改和删除自定义知识卡，修改结果保存在当前浏览器。快捷提问用于演示典型路径；对话可清空，低置信度问题可以生成一张本地待跟进工单并复制摘要。用户反馈只记录本次回答“有帮助/没解决”，用于当前浏览器中的会话统计。

静态 GitHub Pages 版本必须完整可用，不依赖 API Key。可选 Node 服务端只负责安全代理 OpenAI-compatible Chat Completions 请求，密钥不进入浏览器。项目不包含真实订单系统、登录、多租户、客服排班、全渠道接入或持久数据库；这些能力会掩盖 68 号项目的核心练习：知识库检索、意图路由、可信降级和完整客服闭环。

## 架构、数据流与失败处理

`support-core.js` 是零依赖 UMD 模块，供 Node 测试、浏览器和服务端共同使用。它负责文本归一化、中英文关键词切分、FAQ 字段清洗、知识库去重、意图打分、FAQ 相关度排序、本地答复生成，以及 AI 响应中答案、意图、置信度、引用 ID 与建议追问的校验。路由器只引用启用的知识卡；当最佳匹配不足阈值时返回 `needsHandoff`，并使用可理解的兜底文案。

浏览器控制器维护对话、当前路由、知识库、反馈和待跟进工单。发送问题后先同步生成可信本地答案，再向同源 `/api/reply` 请求增强结果；只有服务端返回通过核心校验、且引用 ID 确实存在的内容时才替换当前答复。网络失败、未配置、超时或无效内容都保留本地答案，并把状态标成“本地路由”，避免把规则匹配伪装成在线 AI。

`server.js` 使用 Node 内置 HTTP、Fetch 与文件 API。请求体限制为 64 KiB，知识卡不超过 40 条，对话上下文只保留最近 8 条；`AI_API_KEY`、`AI_MODEL` 和 `AI_BASE_URL` 从环境变量读取。上游响应通过共享核心清洗，错误只返回稳定代码，不泄露密钥、提示词或原始提供商响应。单元测试覆盖意图、排序、停用卡片、低置信度、恶意字段与 AI 引用；服务测试覆盖静态入口、请求限制、未配置降级、成功代理和上游错误隔离。

## 视觉系统与响应式布局

视觉来自老式电话交换台，而不是常见的渐变 AI 仪表盘。色板为交换台绿 `#173F3A`、搪瓷纸 `#F3E9D2`、铜线 `#B96F3A`、信号蓝 `#4C8AA7`、告警红 `#C94F3D`、墨黑 `#17201F`。标题使用 `Bahnschrift SemiCondensed` / `Microsoft YaHei`，正文使用 `Segoe UI`，意图、置信度和时间使用 `Cascadia Mono`。结构标签只表达真实客服动作：`会话线路`、`意图端口`、`知识卡`、`人工接管`。

桌面端左侧是宽阔的会话纸带和输入台，右侧是固定的路由面板。页面的唯一标志性元素是一条“铜质跳线”：问题进入后，线路依次点亮“来电 → 意图端口 → FAQ 插孔”，让答案来源一眼可见。知识卡使用可替换的窄纸签样式，置信度是刻度表而不是装饰性环形图。回答进入时只做一次纸带滑入，其他控件保持克制。

移动端把路由面板放在会话下方，三段线路变成横向流程，知识库管理使用全宽原生对话框。所有操作目标至少 44px，焦点环清晰，状态通过 `aria-live` 播报；`prefers-reduced-motion` 下取消纸带位移和线路脉冲。桌面 1440px 与手机 390px 均不得出现横向溢出，空状态、失败状态和人工接管状态都给出下一步操作。
