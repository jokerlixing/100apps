# App 057 · Relay Bench 设计说明

## 目标

Relay Bench 是一个面向前端开发者的本地 CORS 代理与请求调试台。页面只完成一件事：把浏览器原本会被跨域策略拦截的开发请求，经由本机受控代理转发到明确允许的远端主机，并把响应状态、耗时、响应头和正文原样带回。

完成标准：

- `node server.js` 即可启动，默认只监听 `127.0.0.1:4057`。
- 支持 GET、POST、PUT、PATCH、DELETE、HEAD 和 OPTIONS，预检请求获得完整 CORS 响应头。
- 目标仅允许 HTTP/HTTPS，必须命中主机白名单；DNS 解析后的环回、私网、链路本地、保留地址全部拒绝。
- 跳转的每一跳都重新执行白名单和私网校验，禁止把公开 URL 当作进入内网的跳板。
- 请求体、响应体、超时和跳转次数都有硬限制；Cookie、来源、逐跳头和上游 `Set-Cookie` 不转发。
- 调试台可编辑方法、URL、请求头和正文，并显示真实响应、失败原因及可复制的 `fetch` 示例。
- 桌面和移动端均可操作，键盘焦点清晰，动效遵守 `prefers-reduced-motion`。

## 方案取舍

1. **本机受限 Node 代理（采用）**：无第三方依赖、启动成本低，能落实 DNS 和请求大小限制，也符合“解决本地开发跨域”的题目边界。
2. **任意目标的开放中继**：使用最省事，但会成为 SSRF、流量滥用和凭证外传入口，不提供这一模式。
3. **Serverless 公网网关**：方便远程使用，但需要部署账户、计费边界和滥用防护，超出本项目的本地工具定位。

默认白名单只包含 `api.github.com`，让仓库接口示例开箱可用。其他主机通过 `PROXY_ALLOWED_HOSTS` 显式配置，支持逗号分隔的精确主机和 `*.example.com` 子域模式；`*` 只在开发者主动配置时开放公网主机，私网拦截仍然生效。

## 视觉方向

界面取材于网络机柜里的配线架，而不是常见的黑色终端或彩色渐变控制台。

- `porcelain #F4F6F3`：冷瓷工作台底色
- `rack #18222C`：机架、标题和边线
- `panel #FFFFFF`：编辑与响应工作面
- `link #2764F5`：浏览器侧跳线与主操作
- `signal #FF6238`：活动脉冲和失败状态
- `safe #2AA77A`：已连接、允许和成功状态

标题使用 `Arial Narrow` / `Bahnschrift Condensed` 的设备铭牌感，正文使用 `Segoe UI` / `Microsoft YaHei`，URL、请求头和遥测使用 `Cascadia Mono` / `Consolas`。

记忆点是一条横跨页面的“请求跳线”：浏览器、策略闸门、远端主机和响应四个插孔通过实线连接。发出请求时只有一个脉冲沿线移动；成功、拒绝和断开分别改变插孔灯色。这条线既是视觉主角，也是请求状态的真实解释。

```text
+--------------------------------------------------------------------+
| RELAY BENCH / 057            LOCAL ONLY · ALLOWLIST: 1 HOST       |
+--------------------------------------------------------------------+
| [BROWSER] ===== [POLICY GATE] ===== [REMOTE] ===== [RESPONSE]     |
+---------------------------------+----------------------------------+
| REQUEST PATCH                   | RETURN MONITOR                   |
| method + target URL             | 200 · 184 ms · 6.2 KB           |
| headers                         | response headers / body          |
| body                            |                                  |
| [SEND THROUGH RELAY]            | [COPY FETCH]                     |
+---------------------------------+----------------------------------+
| SAFETY STRIP · loopback bind · private networks blocked · limits  |
+--------------------------------------------------------------------+
```

## 架构与数据流

- `proxy-policy.js` 保存无服务状态的安全策略：白名单解析、主机匹配、IP 分类、DNS 校验、请求/响应头过滤。
- `proxy-client.js` 先校验目标并锁定已解析的公网 IP，再使用 Node `http` / `https` 请求该地址，同时保留正确的 Host 与 TLS SNI；每次跳转重新执行同样流程。
- `server.js` 提供静态文件、`/health`、`/config` 和 `/proxy?url=...`。它读取受限请求体、调用代理客户端，并为正常与错误响应统一添加 CORS 头和请求追踪号。
- `app.js` 加载公开配置，管理调试表单和跳线状态，将文本或 JSON 响应安全地渲染到页面，并在本地保存最近一次请求草稿。
- 服务不会记录请求正文或认证头。日志只包含追踪号、方法、目标主机、结果、字节数和耗时。

## 错误处理

- 输入缺失、协议非法、白名单不匹配、私网地址、请求过大和方法不支持分别返回稳定的错误代码与可修复说明。
- DNS 失败、连接失败、超时、上游过大和跳转过多统一返回 JSON 错误，不泄露调用栈。
- GitHub Pages 只能展示静态调试台；检测不到本地服务时，页面明确给出启动命令，不把静态页面伪装成可工作的代理。

## 验证

- Node 单元测试覆盖白名单、通配子域、IPv4/IPv6 私网识别、DNS 结果、头部过滤和错误代码。
- 本地上游集成测试覆盖方法/正文转发、响应头、重定向、超时和响应大小限制。
- 服务端测试覆盖健康检查、公开配置、CORS 预检、缺少目标、禁止方法和成功响应。
- 浏览器检查覆盖成功、拒绝、服务离线、无效请求头、复制示例，以及 1440×900 和 390×844 布局。
