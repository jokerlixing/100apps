# App 072 全栈电商 Demo 设计

## 产品边界与核心路径

72 号应用命名为 **COUNTER/72**，服务于参加周末设计市集、希望提前锁定独立品牌小物并到场取货的顾客。页面只承担一条完整路径：浏览摊位商品，按库存加入购物袋，在实时取货票上核对金额，填写称呼、手机号后四位和取货时段，提交订单，再在订单台查看或推进履约状态。它不接入真实支付、物流、账号或个人住址；所有付款文案都明确为“到场支付”，避免把演示结算伪装成真实交易。

商品目录固定为十二件来自纸品、陶器、织物和灯具摊位的设计小物。搜索、摊位筛选、库存提示和购物袋在静态版本中完整可用。订单状态只包含“待备货 → 可取货 → 已完成”，未进入“可取货”的订单可以取消。每次下单生成可读订单号和六位取货码；客户端幂等键避免用户双击产生重复订单。订单台只展示当前浏览器用随机 `shopKey` 创建的订单，因此它是清晰标注的单店演示隔离，不声称提供真实身份认证。

## 架构、数据流与失败处理

采用零依赖模块化单体。`shop-core.js` 是 UMD 领域核心，负责购物袋清洗、库存上限、服务端可信计价、订单输入校验、状态机、订单号/取货码格式和安全序列化。浏览器控制器使用相同核心先完成本地结算：静态 GitHub Pages 或 API 不可用时，订单写入 localStorage 并明确标记“本地订单”；Node 服务可用时，`POST /api/orders` 返回服务端重算后的订单，浏览器再替换本地草稿。任何网络失败都不会清空购物袋或伪造成功。

`server.js` 使用 Node 内置 HTTP、Fetch/File API，不引入运行时依赖。固定商品目录由核心模块提供；订单写入可配置的 JSON 文件，使用进程内串行写队列和临时文件重命名降低部分写入风险。请求体限制为 32 KiB，所有价格、库存和状态转换由服务端复算；`GET /api/orders?shopKey=...` 只返回同一店铺键的订单，`PATCH /api/orders/:id` 同样要求店铺键并只允许受控状态转换。该 `shopKey` 只是 Demo 隔离键，不是认证或授权方案。异常响应使用稳定错误码，不回显文件路径或内部堆栈。

架构取舍是“静态优先的模块化单体”，而不是纯前端或带数据库/登录的完整商城。纯前端无法诚实体现服务端可信计价和持久化；SQLite、用户系统和支付会扩大部署与安全范围。JSON 存储适合单进程作品集演示，文档会明确它不适用于多实例和真实商业数据。目标是 1440px 与 390px 无横向溢出，核心交互即时响应，服务端测试使用临时目录且不污染仓库。

## 视觉系统与响应式布局

视觉来自周末创意市集的折叠摊位与打孔取货票，而不是通用电商卡片。色板为篷布蓝 `#B9D8F2`、摊位钴蓝 `#2447D8`、路锥橙 `#FF5C35`、票据薰衣草 `#EAE4FF`、沥青墨 `#182238`、展台白 `#F7F4ED`。标题使用 `Arial Black` / `Microsoft YaHei` 的紧凑粗体，正文使用 `Segoe UI`，价格、库存、订单号和取货码使用 `Cascadia Mono`。结构标签只描述真实动作：`逛摊`、`取货票`、`确认预订`、`订单台`。

桌面端顶部是一条可横向阅读的摊位棚布，主体左侧为商品陈列架，右侧固定一张打孔长票。购物袋不是遮挡页面的抽屉：每次加入商品，票据会向下延长一格并更新总计，这个“吐票”动作是唯一主动画。商品图形由 CSS 几何、编号和材料标签构成，不加载不稳定的外部图片。提交后票据沿虚线撕下，露出订单号和高对比取货码。订单台采用真实履约队列，状态按钮紧邻当前订单，避免装饰性统计面板。

移动端先陈列商品，底部提供固定的“查看取货票”按钮；票据以页面内弹层出现，结算仍是原生 `<dialog>`。触控区不小于 44px，焦点环明确，状态变化写入 `aria-live`。`prefers-reduced-motion` 下取消吐票和撕票位移。空购物袋、无搜索结果、API 离线、输入错误、库存不足和重复提交都提供下一步动作。

## 验证重点

- 核心测试覆盖购物袋清洗、库存上限、金额复算、输入校验、幂等键、订单编号、店铺隔离和受控状态转换。
- 服务测试覆盖静态白名单、路径穿越、请求体限制、服务端价格防篡改、重复提交、JSON 持久化恢复和错误隔离。
- 浏览器冒烟覆盖搜索/筛选、增减商品、结算校验、成功取货票、订单状态推进、刷新恢复、强制本地模式、390px/1440px 布局、键盘焦点与运行时错误。
- 追踪器把第 72 项更新为 `COUNTER/72`、GitHub Pages 链接和完成状态，同时保留 68–71 的当前状态。
