# App 082 微信小程序商城设计

## 产品定位

App 082 是一个可直接部署到 GitHub Pages 的微信小程序商城模拟器。它不依赖微信登录、真实支付或远程数据库，用户在普通浏览器中即可完成一次可信的购物流程：浏览山货、筛选与查看详情、加入购物车、填写收货信息、核对优惠与运费、模拟支付并回看订单。

具体主题为“云岫山货铺”，面向想快速购买当季山货的城市家庭。页面的唯一核心任务，是让首次访问者在三分钟内完成一笔模拟订单，同时清楚知道价格如何计算、信息保存在哪里以及支付并非真实扣款。

## 方案比较与决定

### 方案 A：纯静态商品橱窗

实现速度最快，但只能浏览和加购，无法满足“完整下单流程”，也不足以展示 L4 项目的产品闭环。

### 方案 B：浏览器中的小程序商城模拟器（采用）

使用原生 HTML、CSS 与 JavaScript 实现移动端小程序体验，并在桌面端扩展成“货架 + 订单纸带”的工作台。商品、购物车、地址和订单都保存在本地，GitHub Pages 可直接部署，自动化测试也能覆盖完整流程。

### 方案 C：真实微信小程序 + 云开发

最接近生产环境，但需要 AppID、微信开发者工具、云环境和登录授权，无法通过公开部署链接立即验收，也超出本项目完成闭环所需范围。

## 体验与信息架构

应用包含四个主视图：逛山货、分类、购物车、我的订单。用户可以搜索商品、按分类和推荐标签过滤、打开商品详情并选择数量。购物车以底部纸带形式持续显示件数和合计，结算页依次完成地址、配送、优惠与支付方式核对。提交成功后生成可追踪订单号并写入本地订单列表。

结算提供明确规则：满 99 元免基础运费；优惠码 `WELCOME12` 在商品小计满 68 元时减 12 元；优惠不产生负数；库存不足时数量被限制。支付只模拟微信支付确认，界面在提交前和成功页都说明不会发起真实扣款。

空购物车、搜索无结果、地址缺失、库存不足和本地存储不可用都有直接的下一步指引。用户刷新后，购物车、收货地址、收藏状态和订单仍保留在当前浏览器。

## 视觉方向

视觉来自山货铺的竹筛、牛皮纸价签与盖章收据，而不是通用电商渐变卡片。

- 松针墨 `#173C35`：标题、导航和主要操作
- 米纸白 `#F6F0E1`：页面底色
- 柿子橙 `#E85B36`：价格和关键状态
- 茶叶青 `#78946D`：筛选与辅助状态
- 封箱金 `#F0B94B`：优惠和高亮
- 炭黑 `#252723`：正文

标题使用 `STKaiti / KaiTi` 形成手写货签感，正文使用 `Microsoft YaHei / PingFang SC`，订单号、规格和金额使用等宽字体。桌面端是左侧货架、右侧订单纸带；移动端转换为单列小程序，并使用底部导航和可拉起购物车抽屉。

标志性元素是一张连续的“订单纸带”：从悬浮购物车、结算摘要到支付成功页保持相同的齿孔、虚线和盖章语言，让完整下单流程在视觉上连成一件事。动效只用于商品入篮、纸带展开和成功盖章；系统偏好减少动效时全部关闭。

## 架构与数据流

`shop-core.js` 是无 DOM 的 UMD 核心模块，负责金额计算、购物车归并、库存约束、结算校验和订单生成，可被浏览器与 Node 测试共同使用。`app.js` 负责视图状态、事件绑定、模板渲染和 `localStorage` 持久化。`index.html` 提供语义结构与对话框骨架，`styles.css` 提供响应式视觉系统。

商品目录随代码发布，订单仅在浏览器本地生成。金额统一以整数分计算，避免浮点误差。订单创建接受可注入的时间与随机源，使测试结果稳定。存储层对 JSON 损坏与配额错误进行容错，失败时仍允许当前会话继续下单，并显示数据未持久保存的提示。

## 可访问性与验证

所有交互控件可键盘操作并有清晰焦点；抽屉和对话框使用原生 `dialog`，关闭后焦点返回触发按钮；表单错误与购物车变化通过状态区域播报。商品图片使用内嵌 SVG 图形与中文替代文本，不依赖第三方图片服务。

验证包括：核心逻辑单元测试、JavaScript 语法检查、桌面和 390px 手机端浏览器流程、刷新持久化、优惠/运费计算、表单错误、空状态、订单创建、无横向溢出、控制台无错误以及根追踪器 82 号条目的名称、链接和官方完成状态。
