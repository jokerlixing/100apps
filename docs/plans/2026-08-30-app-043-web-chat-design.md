# App #043 PATCH/43 网页聊天室设计说明

## 产品定位

面向临时项目组、活动同伴和需要快速开一个无账号群聊的小团队。页面的单一任务是：让成员通过同一个房间链接进入群聊，看到最近历史、在线成员与输入状态，并在断线或刷新后继续当前会话。

## 方案比较

1. **托管聊天服务**：公网协作最省事，但需要账号、密钥、配额和持续外部依赖。
2. **轮询或 SSE**：历史读取简单，却不适合双向输入状态、低延迟 presence 和即时消息确认。
3. **WebSocket 内存房间 + BroadcastChannel 回退（采用）**：本地启动时支持真正跨设备群聊；GitHub Pages 自动使用同浏览器多标签房间，无需配置即可体验完整交互。

## 标志性元素

消息流是一卷从总机吐出的打孔纸带：每条消息左缘有一列与发送者颜色一致的“纸孔”，相邻消息之间由细线路连接。页面顶端只有一条信号线会在新消息到达时从发送者插孔亮到消息区；其他元素保持克制，避免做成通用圆角气泡聊天模板。

## 消息与历史模型

- 每条消息包含 `id`、`clientId`、`name`、`color`、`text`、`createdAt` 与可选 `replyTo`
- 服务端按房间保留最近 120 条消息，新成员加入后先收到历史与成员快照
- 消息 ID 幂等：断线队列或重发不会在历史中生成重复消息
- 单条最多 600 字；连续空白规范化但保留换行，不解析 Markdown，不渲染 HTML
- 回复只保存目标消息 ID；目标仍在历史时显示发送者与一行摘要，过期后显示“原消息已离开历史”
- 自己发送的消息先以“发送中”进入本地列表，服务端回显后变为“已送达”

## 实时协议

消息统一包含 `v`、`type`、`room`、`clientId` 和 `ts`。客户端发送 `join`、`chat:send`、`typing` 和 `ping`；服务端发送 `snapshot`、`presence`、`chat:message`、`typing`、`pong` 与 `error`。

输入状态最多保留 4 秒且不进入历史。单成员 10 秒内最多发送 8 条聊天消息；通用事件还受每 5 秒 180 条的窗口限制。房间最多 30 人、单条 WebSocket 消息最大 32KB。服务端不保存 IP、账号或持久数据。

## 部署与回退

- `npm start` 启动 HTTP + WebSocket 同源服务，适合本机和局域网真实群聊
- GitHub Pages 无法接受 WebSocket Upgrade，前端会使用房间级 BroadcastChannel
- BroadcastChannel 只连接同一浏览器、同一站点的标签页，界面明确显示“本机线路”
- WebSocket 断线时保留未送达消息并切换本机线路；重连收到快照后合并历史并补发自己的缺失消息
- 进程重启会清空历史；界面和 README 明确告知这一边界

## 非功能与安全

- 房间最多 30 人、历史 120 条、消息 600 字、消息载荷 32KB
- 房间 ID、客户端 ID、消息 ID、颜色、姓名、文本和回复目标均验证
- 前端只用 `textContent` 渲染远端内容，禁止 HTML 注入
- 键盘可完成输入、发送、取消回复和成员导航；可见焦点并尊重减少动态效果
- 390px 下成员板变为横向插孔条，消息区保留至少 440px 高度且页面不横向溢出

## 验收标准

- 两个同房间 WebSocket 标签能同步消息、在线成员和输入状态
- 新成员加入后收到最近历史，刷新不会制造重复消息
- 不同房间互不串线，超长、空白、过频和非法消息被拒绝
- 回复引用、发送中/已送达、字符计数与 Enter/Shift+Enter 行为正确
- 两个静态托管标签可以通过 BroadcastChannel 群聊并恢复历史
- 断线状态和协作范围文案准确，不把本机回退称为公网聊天室
- 桌面和窄屏布局可用，远端文本不会执行 HTML
- 追踪器显示 43/100，第 043 项链接和完成态正确
